# `audit-scope --rotation N` — the random rotation

The procedure `audit-scope` follows when invoked with `--rotation N`.
The entry file (`SKILL.md`) owns everything a rotation shares with a
scoped run — classification and the dimensions (steps 2–3), the
cross-check (4), the linter screen (5), the dedup set, fingerprints,
the parked filing call and body fields (6), and the fold rule (Notes). This file owns only what is specific to a rotation.

A rotation is a fixed sequence of **seven units** — four random files
plus three structural passes. `N` (default 1) is how many independent
rotations to run back to back; each samples afresh.

## When to reach for it

**An ad-hoc invocation, never a default.** No skill runs it:
`housekeeping` runs no audit, and auditing reaches the board as a
planning-filed audit issue naming one target, run as a scoped
`audit-scope`. The reason is **targeting, not cost** — a random rotation
in a heavy-feature phase audits code about to be rewritten, and one pass
filed fifteen parked findings, several against files open Backlog issues
already covered. Reach for it deliberately, when breadth is wanted; a
planning session may also file a random-target pass as an audit issue
when its heartbeat wants breadth rather than depth.

**It is finite.** It runs the seven units `N` times, files what they
surface, and **stops** with one `DONE` line per rotation. No `/loop`,
no finding cap — the rotation *is* the bound. Nothing runs it on a
cadence; the planning session's audit heartbeat is what keeps the repo
audited.

## The seven units

**FILE is the connective tissue** — four of the seven — so every
rotation samples real code between the structural passes:

```txt
1. FILE       — a random non-generated file        → engine steps 2–5
2. SUBSYSTEM  — one random subsystem               → internal-architecture lens
3. FILE       — another random non-generated file  → engine steps 2–5
4. INTERFACE  — one random inter-subsystem seam     → seam / contract-drift lens
5. FILE       — another random non-generated file  → engine steps 2–5
6. LAYOUT     — repo-layout + spec-health pass      → one agent
7. FILE       — another random non-generated file  → engine steps 2–5
→ per unit: cross-check, dedup, file/fold findings (parked: Todo + milestone)
→ at the end: DONE
```

Each structural unit picks **one** subject **at random**, not a fan-out
over all of them — sampling one per rotation reaches the tail over
repeated runs and keeps a rotation bounded (one agent each, not ≈15).

As **each** unit's findings come back, run them through cross-check
(structural units only), dedup, file and announce **before** the next
unit, so findings land promptly. Prepend the sub-agent brief to every
structural agent and don't narrow it — a structural unit is *meant* to
range over its subject.

## Start of each rotation

1. **Sync the worktree to `main`**, two bare commands:

   ```sh
   git fetch origin main
   git merge --ff-only origin/main
   ```

   If the fast-forward fails (the worktree drifted), warn and continue —
   never force or rebase. This is the rotation's one repo operation; it
   pulls in others' merged work and introduces nothing of its own.

1. **Rebuild the dedup set** from live Linear (`SKILL.md` step 6).

1. **Read the registry** — subsystems (`name (kind, risk): roots`),
   interfaces (`A <-> B: contract`), skip-globs — from
   `docs/conventions/audit-registry.md`, with the Read tool. Never edit
   it; `review-pr` maintains it on the PR path.

## FILE unit (1, 3, 5, 7)

Selection is **random by design** — there is no coverage cursor (no
local state), so randomness is what reaches each subsystem's tail. Don't
anchor the four FILE units on one subsystem.

- **Pick a random subsystem**, leaning toward higher `risk` but never
  excluding a low-risk one.
- **Pick a random eligible file in it.** Enumerate its tracked files
  with one bare `git ls-files <root>` per `roots` glob, then drop any
  path matching a skip-glob.
- **Screen for generated content.** Read the first ~15 lines
  (`limit: 15`) for `@generated`, `DO NOT EDIT`, `Code generated by`,
  `AUTOGENERATED`, or binary content; on a match pick another file. A
  rotation persists no new skip-glob — if a whole family keeps being
  screened out, say so, so one is added on the PR path.
- **Run engine steps 2–5 on that one file** — classify, dimensions,
  cross-check, linter screen — with no plan gate. The survivors go
  straight to dedup: their cross-check already ran.

## SUBSYSTEM unit (2)

One random subsystem (weighted by `risk`, none excluded); **one** agent
auditing its **internal** architecture:

- layering & dependencies within it (a layer reaching into another's
  internals — e.g. the matcher knowing `Market`'s storage layout);
- paradigm & consistency (drift from its intended model — the on-chain
  eCLOB, the shared-math contract — divergent idioms, incoherent
  structure);
- invariant coverage (each invariant it relies on — the program's
  `I1`–`I6` share-accounting set, treasury-vs-vault, vault lifecycle —
  traced across its paths);
- internal duplication, and naming.

`fingerprint_slug`: `<subsystem>:<topic-slug>`.

## INTERFACE unit (4)

One random registry interface; **one** agent auditing the **seam**,
since seams are where contract drift hides:

- schema / contract drift across the boundary (e.g. the on-chain
  `FillEvent` ↔ the IDL ↔ the generated clients; `sdk/math-core` ↔ the
  program's math ↔ the conformance vectors);
- end-to-end data flow across it;
- shared types / constants duplicated across the seam instead of shared.

`fingerprint_slug`: `<interface-pair>:<topic-slug>` (e.g.
`program-sdk-clients:…`).

## LAYOUT unit (6)

**One** repo-wide agent:

- **Repo layout / hierarchical organization** — directory, module and
  crate placement; a file in the wrong tree; orphaned or redundant
  directories; a helper that belongs elsewhere.
- **Spec health** of `docs/` — sections over- or under-specified, in
  the wrong document, or due a split / merge. Read the specs
  (`architecture.md`, `interface.md`, `market-making.md`) as **subject
  matter, not just ground truth**.

`fingerprint_slug`: `layout:<topic-slug>` or `docs:<topic-slug>`.

Every structural agent returns `path:line` anchors, severity, a one-line
rationale and the slug, and ends with the self-deflation clause.

## Structural cross-check

FILE findings were cross-checked in the engine; SUBSYSTEM / INTERFACE /
LAYOUT findings get engine step 4 here — a fresh skeptic, re-spawning
the lens agent to defend or retract on material disagreement, at most 2
more rounds.

**Structural fingerprints** have no basename, so they are fixed-prefixed
`arch:` — `arch:<fingerprint_slug>` = `arch:<lens>:<topic-slug>`, e.g.
`arch:program-sdk-clients:idl-event-drift`. One prefix across all three
units keeps continuity with fingerprints earlier rotations filed.

## Filing across units

**Fold across units, not only within one.** Keep a running note of the
issues filed *this rotation* and each one's coherence group; when a
later finding joins a filed group, append it to that issue instead of
filing afresh — through the zero-echo writer, which needs no prior read:

```sh
python3 .claude/tools/linear_issue.py append --id <ENG-###> \
  --file <scratchpad>/part-N.md
```

The part carries its own sub-heading and `**Fingerprint**:` line.

**Count the parts before appending — that step is where a rotation
breaks the size bound.** Seven units keep joining later findings to a
group already filed, so the count climbs one finding at a time with no
single decision to grow it. At **five** parts, file the next finding as
a fresh sequential issue, naming the earlier one in a
`**Suspected dependency**:` line — and still **no edge**.

**Structural findings file one detailed proposal issue each** — same
parked call, but they are not atomically fixable, so the body is:

- `**Concern**:` what is structurally wrong and why it matters.
- `**Evidence**:` the files / instructions / spec sections involved,
  with `path:line` anchors.
- `**Options**:` the candidate approaches with their trade-offs.
- `**Recommended**:` the approach you'd take, and why.
- `**Likely decomposition**:` the smaller, independently-landable steps
  it splits into, so triage can break it up.
- `**Fingerprint**:` the `arch:` key. Mandatory.
- `**Discovered by**: audit-scope rotation <unit> @ <commit SHA>`

Priority 3 — proposals to triage, not pre-approved work. Title by area:
`arch: decouple the matcher from Market storage layout`.

**Why parked matters more here.** A rotation files the most issues
unattended; thirty or forty findings queued into the Backlog would be
both board bloat and bootstrap-read bloat for the most expensive
session in the fleet. *Rejected alternative, recorded so it is not
re-derived:* a doc-based findings inbox (by analogy to `trim-context`)
relocates that bloat into the planning session and, decisively, breaks
dedup — dedup searches *issues* for a fingerprint, so findings in a
document are refiled every pass.

## Announce and finish

Per filed issue, one line — counts and titles only, never bodies:

```txt
FILED ENG-### [<dimension>/<severity>] <subject> — <title>
```

Close the announcement saying plainly that the findings are **parked
under the Audit findings milestone and await sequencing** — a rotation
must not read as having queued work.

If at least one **high-severity** issue was filed, send exactly **one**
`PushNotification` naming the top one; otherwise send none.

After the seventh unit, print one line and stop (or start the next of
the `N` rotations):

```txt
DONE audit-scope rotation <i>/<N> | filed <t> parked Todo (h/m/l) | deduped <d>
```

## Notes

- Noise control is layered: the engine cross-check (per FILE unit) and
  the structural cross-check, live-Linear dedup against open **and**
  resolved issues, the fixed seven-unit bound, and high-severity-only
  push notifications.
- To graduate this to a scheduled cloud routine, first confirm the Linear
  MCP authenticates in headless runs; if it doesn't, filing breaks and
  the rotation belongs in an interactive session.
